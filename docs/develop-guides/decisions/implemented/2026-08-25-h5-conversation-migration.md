# H5 历史会话按来源事实迁移

状态：implemented
类型：feature
Owner：backend/scripts/migrate_jd_ai_h5_conversations.py

## 问题

旧 H5 平台与 Yuxi 的会话、消息和用户身份结构不同，不能直接复制数据表。迁移还必须避免重复写入，并允许先核对源数据再影响目标 PostgreSQL。

## 决策

使用离线脚本按固定截止时间读取指定 H5 应用的数据，将 `sys_user.user_name` 映射为 OA UID，并把会话与消息转换到 Yuxi 当前模型。脚本默认只预检，显式传入 `--apply` 后按会话独立事务写入；来源、批次和源记录 ID 保存在扩展元数据中，已有来源会话按 `thread_id` 幂等跳过。

PostgreSQL 的 `conversations` 与 `messages` 是迁移结果 Owner。脚本只迁移附件元数据，不复制文件实体，也不迁移 LangGraph checkpoint、Agent Run 或工具调用记录。前端继续通过现有历史消息接口读取迁移结果。

## 替代方案

- 直接跨库复制表：两套 schema、用户标识和约束不同，无法形成可验证的目标数据。
- 在在线请求中动态读取 H5：会长期引入跨系统依赖和双事实源，不适合作为历史数据收口方案。
- 一次性手工 SQL：难以覆盖消息转换、会话级回滚、失败清单和安全重跑。

## 后果

每套独立目标数据库需要执行一次迁移。后续重跑会跳过已迁移会话，因此能补充新会话，但不会向已迁移旧会话追加后来产生的消息。源数据异常按会话记录失败，不阻止其他会话导入。

## 验证

- 容器内单元测试覆盖 OA UID、消息转换、异常会话原子跳过和查询范围。
- Python 编译检查验证迁移脚本可加载。
- 真实迁移通过固定截止时间完成预检、小批量写入和全量写入，并在页面验证历史消息回显。
