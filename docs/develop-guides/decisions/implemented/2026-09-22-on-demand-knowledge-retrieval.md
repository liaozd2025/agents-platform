# 基于知识库描述的大模型选库

状态：implemented
类型：architecture
Owner：backend/package/yuxi/services/knowledge_retrieval_policy.py

本文面向智能助手维护者，说明描述选库、任务范围与执行边界。范围不包含向量索引、分块、重排模型或生产部署。本决定取代[历史检索范围路由](../archived/2026-09-08-knowledge-retrieval-routing.md)。

## 问题

默认查询全部可读共享库会对缺少相关资料的任务产生无效检索。问题类别或少量排除词无法表达每个知识库能补充的事实；前置检索与工具各自选择范围，也无法保证用户的明确限制贯穿任务与子任务。

## 决策

每轮先读取用户可读且智能体已启用的知识库名称、描述与 ID，再使用当前有效模型，根据问题、最近对话和已有来源概况逐库输出 `select / skip / uncertain`。允许零个或多个选择；候选过长时按上下文容量分批并保持同一任务判断，无法容纳时显式失败。服务端校验候选覆盖、唯一 ID、结构与范围，随后只对选中的库执行内容检索。

知识库缺少描述时标记 `missing_description`，暂按库名判断，并向模型提供提示管理员补充描述的要求。影响回答或任务范围的歧义进入简短追问。名称、描述和知识原文均是待判断数据，其中的指令不能扩大权限。选择模型只判断可能用途；回答引用仍以实际取得并采用的来源为准。

候选包括全局、组织和私人库。后端最终执行用户实时读取权限、智能体启用集合、明确任务范围和本轮选库结果的交集。任务范围与本轮目标分别保存：明确查询某库受到尊重；只限定“只用 A”不强制每轮检索。普通追问沿用任务范围，明确新任务重新判断，任务边界不明时不扩大既有范围，明确缩小的限制仍生效，并先追问。

聊天服务把可信范围和前置检索审计保存到当前 `AgentRun.input_payload`，在持有租约时与会话范围一起提交，再启动智能体和子任务。有效范围的保存独立于内容检索是否成功；会话更新只改变范围字段，保留同期附件和模型更新。锁定 Run 时刷新持久值，使用最新租约校验执行者。

子 Run 只从父 Run 的已提交允许集合继承硬范围；恢复只读取本次 Run 已固化的范围。客户端 Agent 配置、请求元数据和线程创建不能伪造内部范围。检索、搜索、打开、定位、思维导图和下载工具每次重新核验权限，撤权后不使用缓存目录继续读取。

新增事实需求可调用 `select_kbs` 在任务范围内重新选库，工具结果通过既有调用审计记录，前置检索审计保持完整。目录读取、选库调用、内容查询尝试次数与耗时、命中数、错误分别可观察。选库失败、非法输出、权限拒绝和内容服务失败显式报错；合法空结果保留为已检索但无依据，不扩大范围重试。Dify 与 Notion 连接器保留服务失败语义。

运行机制和源码定位见[知识库机制](../../../mechanisms/knowledge-base.md)，配置说明见[知识库入门](../../../intro/knowledge-base.md)。

## 替代方案

| 方案 | 取舍 |
| --- | --- |
| 扩充不检索关键词 | 成本低，但无法表达每个库的用途与混合意图，未采用 |
| 全库检索后过滤 | 已产生内容查询成本，未采用 |
| 仅用户明确选库时查询 | 可预测，但要求用户预先知道库名，未采用 |
| 每库独立模型调用 | 请求数随库数增长，首版采用批量逐库判断 |
| 让主智能体自行决定是否发现目录 | 可能没有检查描述就跳过，前置路径采用显式目录判断 |

## 后果

描述质量直接影响误查与漏查，库维护者需要写明主题、适用对象、覆盖时间和排除内容。首版复用已有描述、模型与检索能力，没有新增目录索引、模型服务或依赖。

选库增加模型调用、延迟和 token；减少内容查询后的净收益必须通过真实模型评测确认。历史摘要长度与模型上下文容量限制仍会影响多轮语义判断。后端强制执行权限和已确认的范围，任务是否切换及资料是否相关仍依赖模型判断。
