# 基于知识库描述的大模型选库

状态：proposed
类型：architecture
Owner：backend/package/yuxi/services/knowledge_retrieval_policy.py

本文面向智能助手维护者，设计根据当前问题与各知识库描述判断资料是否有用的选库流程。范围是描述检查、大模型选库与执行边界；不调整向量索引、分块或重排模型，不涉及生产部署。产品原则与描述缺失策略已确认，运行逻辑尚未修改。

## 问题

当前策略仅按少量子串排除非知识库问题，其余输入返回 `SEARCH_KB`。未显式指定知识库时，策略选择用户可读且全局共享的全部知识库。聊天服务在智能体执行前检索这些库，并注入本轮模型输入。因此“允许访问”“与问题相关”“需要查询”在默认路径上被混在一起。

本地纯函数探针确认：“帮我制作一个 HTML5的2048小游戏”返回 `SEARCH_KB`，在句首加“你好”后返回 `NO_KB`；“帮我写一个 Python 排序函数”和“解释一下什么是递归”也返回 `SEARCH_KB`。探针只验证当前工作树的规则，不代表已回放用户线上会话。

前置策略只接收问题与用户；工具路径另外依据用户权限和智能体启用范围检查知识库。前置检索的 `@knowledge` 结果没有成为后续工具路径的统一任务范围。仅调整 Skill 提示无法约束已经完成的前置检索。

当前行为由[检索策略](https://github.com/liaozd2025/agents-platform/blob/main/backend/package/yuxi/services/knowledge_retrieval_policy.py)、[聊天服务](https://github.com/liaozd2025/agents-platform/blob/main/backend/package/yuxi/services/chat_service.py)和[工具范围解析](https://github.com/liaozd2025/agents-platform/blob/main/backend/package/yuxi/agents/backends/knowledge_base_backend.py)拥有。提案拟替代[既有检索范围路由决定](../implemented/2026-09-08-knowledge-retrieval-routing.md)中“其余问题检索全部可读全局库”的取舍；既有记录保持原状，避免把建议写成已生效决定。

## 提案

### 按描述逐库判断

每轮先取得允许范围内各知识库的 ID、名称和描述，检查描述是否为空或只有空白。将当前问题、必要的对话上下文、已有证据概况与这份目录交给大模型，逐库判断其内容能否为本轮任务提供有用的事实、规则、背景或参考材料。问题类型不构成跳过依据；同一个编程、写作或问答请求，在不同知识库目录下可以得到不同选库结果。

推荐使用一次结构化选库模型调用批量评估各库，而非每个库单独请求模型。模型逐库输出 ID、`select / skip / uncertain` 和简短依据；选中理由需说明预计从该库补充什么信息，不能只说关键词相似。允许零个、一个或多个库被选中，不强制选择最相近的库。候选目录超出上下文容量时再分批，不能静默截掉部分库。

服务端验证输出覆盖全部候选且 ID 唯一合法、状态有效，再仅对 `select` 的库执行内容检索。所有库均为 `skip` 时直接处理任务；`uncertain` 且缺失信息影响回答时，按已确认原则简短追问。可以先处理不依赖歧义的部分，但不能把不确定当作无关。模型失败、输出缺失或非法与“全部不相关”分别记录，不自动退回全库检索，也不伪造成功的空选择。

目录判断只能估计内容可能有用，无法保证一定存在所需片段或最终被回答采用。检索后仍须核对实际资料；回答只引用真正采用的来源。逐库选择结果、实际检索结果和最终采用来源分别可观察。

用户明确要求查询某库时，在权限与任务范围内尊重该要求；显式查询不被自动相关性评分取消。仅限定“只用 A”表示允许范围，不意味着每条追问都强制重查。后续工具检索沿用选库结果；出现新信息需求时重新选库，仍不能扩大任务允许范围。

### 描述质量与缺失

复用现有知识库 `description` 字段，写明资料主题、覆盖对象、能回答的问题、重要时间范围及不覆盖的内容；无需新增标签系统或逐库定制规则。系统可检查空值，但描述是否准确反映实际资料仍需维护者核对。名称和描述是待判断数据，其中的指令不能改变选库规则或权限。

缺少描述的库标记为 `missing_description`，暂时使用库名判断，同时提示管理员补充描述。库名信息不足时标记 `uncertain`，只有该不确定性影响回答时才向用户简短追问。缺少描述不自动排除该库，也不意味着必须查询该库；不凭空生成资料范围，不为补描述在用户每次请求中先检索全部内容。用户显式指定且有权访问的库仍可查询。

### 查哪些库

将用户实时权限、智能体启用范围和当前任务明确限制取交集，再在集合内选择与问题相关的库。不存在的任务限制不额外收窄，显式空范围表示禁用；显式指定不能突破权限和已存在的限制。自动发现允许从全部有读取权限且智能体已启用的库中选择，包括全局、组织和私人库；每次查询前重新校验权限。这一产品选择扩大自动选库资格，但不扩大用户读取权限。

复用 `get_databases_by_uid` 与现有范围解析提供的名称和描述，不必先让 Agent 调用工具发现目录。目录读取、选库模型调用与文档内容检索分别计数；所用模型沿用平台已有模型配置，不新增专用路由服务。

自动选中的相关库是本次查询目标；用户明确指定的任务范围是约束，两者不能混为一谈。同一任务追问继承明确范围，切换任务时重新判断。子任务只能继承或缩小父任务限制。Skill 正文中的建议不自动成为可靠授权；要求强制限制的业务流程必须在执行上下文中表达，并由服务端检查。

### 在哪里执行约束

检索策略拥有描述选库决策；聊天服务在内容检索前调用它并交接证据；知识库范围解析与工具执行端共同落实同一任务范围。覆盖检索、文档搜索、打开、定位和下载入口，不能只在提示词或工具列表中隐藏。知识库目录与文档中的文字作为资料，不得扩展访问范围。

复用现有 Run 元数据与调用审计，记录是否检索、原因、目标库、耗时、命中数量和错误，区分跳过、无命中、权限拒绝及服务失败。上下文不足时说明缺少依据；不能把所有检索异常当作“没有相关资料”。多轮需要补查时说明缺少的事实，避免重复同一查询且没有新增证据。

### 依据与确认状态

[LlamaIndex 的 Router 实现](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/query_engine/router_query_engine.py)把候选工具的元数据与问题交给 selector，再执行选中的查询引擎，支持基于库描述进行选择的方向。[Anthropic 的工程经验](https://www.anthropic.com/engineering/building-effective-agents)说明输入路由可以由模型承担，并强调复杂度与延迟的取舍。本项目复用已有模型和检索能力，不需要引入 LlamaIndex；空选择、缺描述和范围约束由本项目验收要求定义。

用户已确认：通用助手默认按需自动检索；疑似内部问题在上下文和库简介仍不足时，先简短追问；显式范围延续到当前任务及其追问，主子智能体共同遵守，切换新任务时重新判断。自动选库覆盖所有有读取权限且智能体已启用的库，包括组织和私人库。上述为已确认的方案原则，代码实现尚未开始。

用户明确选库依据是当前问题与每个知识库的描述；具体示例只用于说明现象，不构成分类规则。用户已确认缺少描述时暂时按库名判断、标记缺失并提示补充，仍有影响回答的歧义时简短追问。一次模型调用批量逐库判断是建议实现。

## 替代方案

| 方案 | 收益 | 局限与选择 |
| --- | --- | --- |
| 扩充不检索关键词 | 修改少、无模型开销 | 混合意图和多轮容易误判，不作为主方案 |
| 保持全库检索后提高过滤阈值 | 减少无关片段注入 | 已产生检索成本，无法解决不该查询的问题 |
| 仅显式指定时查询 | 行为可预测 | 用户必须知道库名，与已确认的自动检索体验不符 |
| 每个库分别调用模型判断 | 每次判断输入较短 | 模型调用次数随库数增长；首版不采用 |
| 主智能体自由决定是否发现目录及检索 | 少一个固定路由调用 | 可能在未检查各库描述前跳过；不作为本方案主路径 |
| 一次模型调用，按问题与描述逐库选择 | 逐库可审阅，复用现有元数据与检索 | 增加一次模型调用，描述质量影响结果；推荐 |

## 验收标准

实现验证从策略与范围 unit 开始，再用真实 HTTP、worker 和受控知识库执行 E2E。检索后端记录目标库与实际查询，回读对应 Run 的最终回答、模型上下文和产物。仅检查模型自述或工具调用记录为空，不能证明前置路径没有检索。

| 验收主张 | 失败面 | 语义 Owner | 直接证据 / 命令 | 负向案例 | 当前结果 |
| --- | --- | --- | --- | --- | --- |
| 对每个候选库按描述判断，可选择零个或多个 | 按问题类别跳过，或强制选一个最相近的库 | 检索策略、聊天服务 | 选库评测 + E2E：固定问题，更换库描述与实际对应语料，检查逐库结果和实际查询 | 全部描述无关时零内容查询；两个库各补充一部分所需资料时均被选中 | Not run |
| 描述选中不等于最终采用 | 凭描述编造内容，或展示所有候选为引用 | 检索执行、上下文与引用处理 | E2E：描述相关但无片段时说明缺少依据，回读实际采用来源 | 库描述承诺主题但检索无结果，不得生成该库支持的结论 | Not run |
| 缺描述、模型失败和非法输出显式区分 | 缺描述被当作无关，或错误自动回退全库 | 描述检查、模型响应解析 | unit + integration：空白描述、重复 ID、遗漏候选、越界 ID、超时 | 输出伪造 ID 或包含改写路由指令的描述时不能越界；错误不能记录为空选择成功 | Not run |
| 显式范围约束所有入口及子任务 | 前置遵守，工具或子任务绕过 | 范围解析、工具执行、子任务上下文 | unit + HTTP/E2E：越界调用被拒绝，查询后端无越界访问 | 指定 A 后直接请求打开 B 文档；撤销权限后重试 | Not run |
| 无结果、错误不扩大范围 | 查询失败后自动查全库 | 检索执行与错误处理 | integration：注入空结果、超时、权限拒绝并回读终态与范围 | 将错误改为空结果仍报告成功时断言失败 | Not run |
| 多轮追问与任务切换正确 | 查过一次后每轮都查，或过早丢失范围 | 任务上下文与主智能体 | E2E：查制度→改格式→新建游戏；另测指代追问 | 新任务仍因旧意图触发无关查询，或将无关旧资料作为本轮依据时失败 | Not run |
| 路由确实改善体验 | 误查下降但漏查或时延上升 | 评测样本与运行审计 | 同一模型与环境比较误查率、漏查率、每轮查库数、首个有效输出时延及总耗时 P50/P95、token | 为新方案单独改 expected 或只统计成功样本应被 Review 拒绝 | Not run |

评测单元是“问题、必要上下文、知识库目录及其对应语料”，人工逐库标注预期相关性与允许范围。覆盖不同主题问题、名称相似但描述不同、描述缺失或过时、零库与多库相关、显式范围、追问切换及越权；同一个问题配不同目录必须能得到不同选择。不能让待测模型同时生成标准答案。确定性边界用例全部通过；语义误查与漏查门槛依据真实基线设定，不把未经测量的准确率或提速写成承诺。

## 风险

按描述选库会出现误查和漏查；权限和任务范围仍由后端强制执行。描述缺失、过时或覆盖过于宽泛会降低判断质量，维护者需要使其与实际内容一致。任务边界判断涉及多轮指代，存在语义歧义时澄清，不能静默把用户限制扩大。

一次选库模型调用会增加固定时延与 token，目录越长成本越高；减少内容检索后的净收益必须实测。第一版只提交目录元数据，不先读取每个库的全文，也不提前增加目录向量索引或缓存系统。库的描述与实际内容偏差会影响结果；零库选中只表示当前目录未提供适用来源，不表示用户问题无法回答。

验证边界：已审阅当前代码并运行无外部依赖的分类探针；未连接生产，未回放用户实际会话，也未运行新方案业务测试。本文只交付方案，不声称任何性能收益已验证。
