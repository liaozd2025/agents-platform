# 组织机构树与子树继承的权限模型

原本 `departments` 是一张扁平表，共享范围通过 `user.department_id` 精确相等来判定，无法表达"集团 / 分子公司 / 部门"的层级授权。我们把它改造成单表自引用的组织机构树（唯一集团根 + 物化路径列），并把共享范围的判定语义从"精确匹配"改为"子树继承"：共享范围选中节点 X，则 X 子树内全部用户获得权限。

## Considered Options

- **节点分类型建模（集团 / 分子公司 / 部门各一种实体）**：权限判定只关心祖先-后代关系，不关心节点类型；分类型会引入一套"部门能否直接挂集团根"之类的跨类型校验规则，没有对应的业务收益。最终只保留一个纯展示用的 `node_type` 标签，不参与任何校验。
- **祖先链每次查库（递归 CTE）**：`scope_matches()` 是同步纯函数，且知识库列表会对每份资源循环调用一次。改成 async 查库会把整条调用链染成 async 并产生 N 次查询。
- **进程内缓存整棵树**：api 与 worker 是两个进程，缓存失效需要额外的跨进程协调。

选择**物化路径**（`departments.path`，形如 `/1/3/7/`）：写路径在建节点和移动子树时维护，读路径零查询，权限判定保持同步纯函数，只改一处匹配逻辑。

## Consequences

- **存量授权语义会随组织调整而漂移**。旧的 `access_level=department` 数据在新语义下变为"该节点及其子树"，将来在该节点下新建子节点时，资源会自动对新子节点可见，而没有人执行过这次授权。我们接受这一点，不做兼容层——让 `department` 同时存在两种判定语义是更坏的结果。相应地，共享范围保存时必须剔除被祖先覆盖的冗余节点 ID，否则节点移动会制造出无人授权过的跨公司授权。
- **`global` 与"共享给集团根"并存**。没有废弃 `global`，因为内置 Agent 与 Skill 的默认共享配置大量依赖它，废弃的迁移成本换不来任何语义收益。两者的区别记录在 `CONTEXT.md`。
- **`admin` 仍是全局角色**，本次不改。资源可见性（共享范围）与管理域是两个独立的权限轴，混在一起会让改动面从"加一列 + 改一个匹配函数"膨胀到重写全部管理路由的鉴权。由此，"创建组织节点时附带创建管理员"这个动作产生的是全局管理员而非该节点的管理员——名不副实，需在界面与文档中写明。
- **组织节点名称改为同级唯一**（`(parent_id, name)`），因为不同分子公司会有同名部门。这使 OIDC 的部门 claim 不再能唯一定位节点：命中 0 个或多个时一律落集团根并告警，不做猜测——猜错等于把人放进错误的子公司并因此看到不该看的知识库。
- **组织机构树的事实来源是 Yuxi 内的人工维护**，OIDC 只用于把人挂到已存在的节点上，不自动创建节点。这部分修正了 `docs/enterprise/2026-08-12-oa-embed-s0.md` 中"不做组织架构同步"的记录：树仍不同步，但人员归属开始依赖 claim 匹配。
