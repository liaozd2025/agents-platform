# 领域文档

约定 engineering skills 在探索本代码库时，应该如何消费领域文档。

## 探索前先读

- 仓库根目录的 **`CONTEXT.md`**（术语表 / ubiquitous language）
- **`docs/adr/`** —— 读与本次改动区域相关的架构决策记录

这些文件**不存在时静默继续**，不要提示缺失，也不要建议提前创建。它们由 `/domain-modeling`（经 `/grill-with-docs` 触发）在术语或决策真正凝固时懒创建。

## 本仓库的既有文档，与上面是什么关系

Yuxi 已有一份 [ARCHITECTURE.md](../../ARCHITECTURE.md)（matklad 风格的代码地图）。它与 `CONTEXT.md` **职责不同，应当共存，不要互相替代**：

| 文档 | 回答的问题 | 内容 |
|---|---|---|
| `ARCHITECTURE.md` | **改哪里** | 目录职责、模块边界、运行链路、架构不变量 |
| `CONTEXT.md` | **叫什么** | 领域术语定义、同义词取舍 |
| `docs/adr/` | **为什么这么定** | 单条架构决策及其取舍与后果 |

探索代码时 `ARCHITECTURE.md` 优先——它是本仓库现成且维护中的入口。

## 使用术语表的词汇

当产出物中出现领域概念（issue 标题、重构方案、假设、测试名），使用 `CONTEXT.md` 中定义的术语；若该文件尚不存在，则沿用 `ARCHITECTURE.md` 与现有代码中的既有命名，不要漂移到同义词。

如果需要的概念在术语表里没有，这是一个信号——要么是在发明项目并不使用的语言（应重新考虑），要么是真实的空缺（记下来交给 `/domain-modeling`）。

## 与 ADR 冲突时要显式说明

如果产出与既有 ADR 矛盾，明确指出，不要静默覆盖：

> _与 ADR-0007（事件溯源订单）冲突，但值得重开讨论，因为……_

## 文件结构

本仓库为单上下文（single-context）：

```
/
├── ARCHITECTURE.md      ← 既有：代码地图
├── CONTEXT.md           ← 懒创建：术语表
├── docs/adr/            ← 懒创建：架构决策记录
└── backend/ web/
```
