# S2：安全底座实施设计（2026-08-13）

## 目标

修掉可行性分析（`2026-08-12-feasibility-analysis.md` 第四节）列出的 P0 安全问题。本阶段**零外部依赖** —— 不需要 OA 团队任何信息，可与 S0 并行执行。

## 验收标准

1. 任意部门的 `admin` 无法读取/导出/删除不属于其可见范围的知识库
2. 模型厂商 API Key、MCP 凭据在库中密文存储，API 响应中脱敏
3. 知识库解析图片不再匿名可读
4. 沙盒无出网、无多余 capability、有资源上限
5. 改密码 / 改角色后旧 token 立即失效
6. 上述每条都有一个**先失败后通过**的测试

## 范围边界（明确不做）

- 不做 `tenant_id` / 多租户改造（已确认「一个 OA = 一个租户」）
- 不做部门隔离的 RLS（属于 S1，依赖 OA 的部门 claim 是否存在）
- 不做审计体系（属于 S3）
- 不改上游既有的分层结构；所有新增逻辑走新文件，降低 rebase 冲突

## T1 · 统一授权模块 + 补齐知识库路由

### 现状（已逐行核实）

`share_config` 三级（`global` / `department` / `user`）已定义并有归一化工具（`backend/package/yuxi/utils/share_config.py`，含 `SHARE_ACCESS_LEVELS`、`EMPTY_SHARE_CONFIG`、`normalize_share_config`），但评估逻辑**重复了三份**，形状几乎相同：

| 位置 | 函数 | 入参形态 |
|---|---|---|
| `repositories/agent_repository.py:139` | `user_can_access_agent(user: User, agent: Agent)` | ORM 对象 |
| `agents/skills/service.py:136` | `user_can_access_skill(user: User, skill: Skill, *, require_enabled=True)` | ORM 对象 |
| `knowledge/manager.py:208` | `_database_info_accessible(user: dict, db_info: dict)` | dict |

三者共同逻辑：`superadmin` → 放行；`created_by == uid` → 放行；`global` → 放行；`department` → int 比对 `department_ids`；`user` → uid 在 `user_uids` 中。

**知识库侧的实际调用情况**（`grep` 全仓确认，与早期估算有出入，以此处为准）：

- `check_accessible`（`knowledge/manager.py:236`）在整个 API 层**只有 1 个调用点**：`server/routers/workspace_router.py:38`
- 列表类端点是安全的 —— 走 `get_databases_by_uid` → `_database_info_accessible`（`manager.py:301`）过滤
- **单库端点全部未校验**

### 需要补齐的路由（精确统计）

| 文件 | 数量 | kb_id 来源 | 现有唯一门禁 |
|---|---|---|---|
| `server/routers/knowledge_router.py` | 35 | 路径参数 `{kb_id}` | `get_admin_user` |
| `server/routers/knowledge_eval_router.py` | 8 | 路径参数 `{kb_id}` | `get_admin_user` |
| `server/routers/graph_router.py` | 3 | **Query 参数** `kb_id`（`/subgraph`、`/labels`、`/stats`） | `get_admin_user` |

合计 **46 条**。注意 `graph_router` 用的是 Query 而非路径参数（`graph_router.py:52/79/96`），**一个统一的路径参数依赖覆盖不了它**，需要两种取参方式。`graph_router.py:24` 的 `/list` 已正确使用 `get_databases_by_uid`，不用动。

### 做法

**新增** `backend/package/yuxi/utils/authz.py`（新文件，不改上游既有文件的内部逻辑）：

```python
def can_access_shared_resource(
    *, user_role: str, user_uid: str, user_department_id: int | None,
    created_by: str | None, share_config: dict | None,
) -> bool: ...
```

纯函数，无 IO，不依赖 ORM。三处既有评估器改为委托给它（**只替换函数体，保留原函数名与签名** —— 上游若改动调用方，冲突面最小）。

**新增** `backend/server/utils/kb_authz.py`：两个 FastAPI 依赖

- `require_kb_access_path` —— 从路径参数取 `kb_id`
- `require_kb_access_query` —— 从 Query 取 `kb_id`

两者都调用 `knowledge_base.check_accessible(user, kb_id)`，失败抛 404（**不要用 403** —— 403 会泄漏"该 kb_id 存在"这一事实，与列表端点的过滤语义保持一致）。

然后给上表 46 条路由挂上对应依赖。

**注意**：`admin` 在 Yuxi 是全局角色（`ADMIN_ROLES = {"admin","superadmin"}`），不是部门管理员。本任务只做"按 `share_config` 校验可见性"，**不改 admin 的语义** —— 那属于 S1。因此修复后 `superadmin` 仍可访问全部（`can_access_shared_resource` 首条即放行），这是预期行为。

## T2 · 凭据加密与 API 脱敏

### 现状

全仓 `grep encrypt|Fernet|AES|cipher` 只命中一个 `redact_redis_url`。无 KMS、无 Vault、无 pgcrypto。

| 凭据 | 列 | 泄漏点 |
|---|---|---|
| 模型厂商 API Key | `model_providers.api_key` `String(500)` | `ModelProvider.to_dict()` **原样返回**（`models_business.py:671`），任意 `admin` 经 GET/list 即可取得全部厂商密钥 |
| MCP 凭据 | `mcp_servers.env` / `headers` (JSON) | `MCPServer.to_dict()` 返回两者（`models_business.py:566-567`）。对非 admin 已正确降级为 `{name, description, icon, enabled, tags}`（`mcp_router.py:94-109`），但 admin 全见 |
| 用户 agent env | `agent_envs.env` (JSON) | 仅本人可见，但整包注入沙盒容器 |

### 做法

已确认「暂无硬性合规、内网离线」，**不引入 KMS/Vault**（YAGNI）。用应用层对称加密：

- **新增** `backend/package/yuxi/utils/secret_box.py`：基于已有依赖 `cryptography>=48.0.1` 的 Fernet 封装，密钥取自新环境变量 `YUXI_SECRET_KEY`
- **启动即校验**：`YUXI_SECRET_KEY` 未设或为占位值时，在 `YUXI_ENV in {prod, production}` 下直接拒绝启动（照抄 `auth_utils.py:_get_jwt_secret_key` 的既有模式，保持一致）
- 密文加 `enc:v1:` 前缀，读取时按前缀判断是否已加密 —— 支持存量明文平滑迁移
- **一次性迁移脚本** 放 `backend/scripts/`，把存量明文就地加密

**脱敏**（这一条比加密更紧急，先做）：

- `ModelProvider.to_dict()` 改为返回 `api_key_masked`（如 `sk-…3f2a`）与 `has_api_key: bool`，**不再返回明文**
- `MCPServer.to_dict()` 对 `env` / `headers` 的**值**做同样处理，键名保留（前端要展示配了哪些项）
- 前端受影响处：`web/src/components/model-management/ModelProviderManagePanel.vue`、MCP 配置面板 —— 编辑时"留空即不修改"，不再回填明文

> `api_key_env`（环境变量间接引用）是更安全的既有替代，内置 provider 用的就是它（`models/providers/builtin.py`）。文档里应引导新配置优先用它。

## T3 · 知识库图片脱离公开桶

### 现状

```python
# backend/package/yuxi/storage/minio/client.py:66
PUBLIC_READ_BUCKETS = {"public"}
KB_BUCKETS = {"documents": "knowledgebases", "parsed": "knowledgebases", "images": "public"}
```

`ensure_bucket_exists()` 对 `public` 桶调用 `_ensure_public_read_access()`。**所有文档解析出的图片进匿名可读桶**，唯一保护是 `object_name` 里的 UUID 混淆（`storage/minio/utils.py:44`）。nginx 还专门开了 `location /minio/public/` 的 GET 直通（`docker/nginx/default.conf`）。

跨部门的合同、报表、证件扫描件只要 URL 泄漏即全网可读，且无任何访问日志。

> 本条在原排期中列在 S1，因其**零外部依赖**且属 P0，移到 S2 执行。

### 做法

- `KB_BUCKETS["images"]` 改到非公开桶（复用 `knowledgebases`）
- 图片改经后端签发**短期预签名 URL** 下发，或走已有的鉴权代理路由；不要保留任何匿名读路径
- nginx 的 `/minio/public/` 收窄到确实公开的资产（如头像），知识库图片不得走此路径
- **存量迁移**：把 `public` 桶中属于知识库的对象迁到非公开桶并改写引用；迁移脚本放 `backend/scripts/`
- 前端图片引用处需同步改造（`web/src/utils/file_preview.js`、Markdown 渲染中的图片 URL）

## T4 · 沙盒硬化

### 现状（`docker/sandbox_provisioner/app.py`）

容器创建参数（`:504` 起）：

```python
"security_opt": ["seccomp=unconfined"],
"tmpfs": {"/home/gem": "rw,exec,mode=777"},
```

**没有** `cap_drop` / `no-new-privileges` / `read_only` rootfs / `mem_limit` / `cpu_quota` / `pids_limit`。

网络做对了一半：`_ensure_network`（`:356`）为每个沙盒建独立 bridge（`:363` 的 `networks.create`），沙盒之间隔离、`app-network` 上的 postgres/milvus/minio/redis/neo4j 不可达。**但没设 `internal=True`，出网完全不受限** —— 无出口代理、无域名白名单、无 DNS 过滤。

已有限制：exec 超时 180s、输出 256KB、空闲 120s。

### 做法

内网离线部署下沙盒本就不需要出网，以下改动零功能损失：

1. `networks.create(..., internal=True)`（`:363`）
2. 去掉 `seccomp=unconfined`，用 Docker 默认 seccomp profile
3. 加 `cap_drop=["ALL"]`、`security_opt` 增 `no-new-privileges:true`
4. 加 `mem_limit`、`cpu_quota`（或 `nano_cpus`）、`pids_limit`，取值走环境变量
5. `tmpfs` 的 `exec` 位保留（skill 脚本需要执行），但收紧 `mode`

**验证顺序很重要**：先加 1、3、4 跑一遍内置 skill（尤其 `mysql-reporter`，它用 `uv run` 执行脚本），确认无回归，再去掉 `seccomp=unconfined`。seccomp 收紧最容易打断解释器，单独一步好定位。

**不在本任务范围**：provisioner 挂载 `/var/run/docker.sock`（`docker-compose.yml:137`）与其单一静态 token 的架构问题。改这个要动部署形态，单独评估。

## T5 · Token 吊销

### 现状

`backend/package/yuxi/utils/auth_utils.py:72` 的 `create_access_token` 签发 7 天 HS256 JWT，claims 仅 `sub` / `exp` / `iss` / `aud`。**无 `jti`、无黑名单、无 refresh token**。改密码、改角色、调部门、离职后旧 token 全部继续有效。

API Key（`yxkey_` + SHA-256）**继承持有者完整角色、无 scope** —— admin 的 key 就是 admin key。

### 做法（本任务只做最小可用的吊销）

- `create_access_token` 增发 `jti`（`secrets.token_urlsafe`）
- 新增 Redis 黑名单，key `auth:revoked:{jti}`，TTL 对齐 token 剩余有效期；用现成的 `yuxi.storage.redis.manager.get_async_redis_client()`
- `get_current_user`（`server/utils/auth_middleware.py:51`）在解码后查黑名单
- **按用户批量吊销**：记录 `auth:pwd_epoch:{uid}`，token 里带签发时的 epoch；改密码/改角色/改部门时递增 epoch，令旧 token 全部失效。这条比单点 jti 更重要 —— 它覆盖"离职/降权"这个真实场景
- 触发点：`auth_router.py` 的改密码、更新用户、删除用户、改部门

**不做**：refresh token、API Key scope 化 —— 前者是体验优化，后者改动面大且需要先定义 scope 模型，都不属于 P0。

## T6 · Skill 远程安装

### 现状

`backend/package/yuxi/agents/skills/remote_install.py:112` 用 `asyncio.create_subprocess_exec` 在 **API/worker 容器内**执行 `npx -y skills add <source>`（仅以临时 `HOME` 隔离），任意 `get_required_user` 可经 `POST /api/skills/remote/prepare` 触发。第三方包先落到 API 容器文件系统，再只读挂进沙盒。无审核、无签名、无版本回滚。

zip 导入那条路有 `_validate_zip_paths` 防 zip-slip，npx 这条没有等价防护。

### 做法

内网离线部署下 `npx` 拉 GitHub/ModelScope **本就不可用**，所以：

- 新增开关 `YUXI_SKILL_REMOTE_INSTALL_ENABLED`，**默认关闭**；关闭时相关路由返回 501 并说明改用离线导入
- 保留既有的 zip 上传导入路径（已有 zip-slip 防护）作为唯一入口
- 若后续需要，再接内部 npm registry —— 不在本任务范围

> 离线部署在这里是安全红利：一个 P0 供应链风险用一个默认关闭的开关就消掉了，不需要设计审核流程。
